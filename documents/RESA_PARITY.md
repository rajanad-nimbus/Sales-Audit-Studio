# ReSA 15.0.1 workflow parity

This map translates the supplied [Oracle Retail Sales Audit User Guide, Release 15.0.1](resa-1501-ug.pdf), into reviewable ZeTSA capabilities. “Covered” means a corresponding workflow is present in the current code; it does not claim production integration or complete end-to-end validation. The guide describes the reference workflow, while ZeTSA keeps external identity, immutable audit history, and independent financial approvals as platform controls.

## Work to close the largest gaps

Agent Activity uses one server-side filter predicate for its cursor-paged browse and bounded full CSV export, so searches and actor/attention filters apply to the complete audit stream rather than only the rows already loaded in the browser.

1. **Keep the regression baseline green.** The backend suite (run with the project virtualenv, Python 3.12) last ran 1,222 passed, 0 skipped, 0 failed with PostgreSQL configured (1,201 passed, 21 skipped without it); the frontend suite runs 226 passing tests with a clean typecheck and production build. Closure now requires auditor sign-off on current totals, rule changes follow the worksheet → submit → approve workflow, and rule errors are raised before a re-total changes anything.
2. **Finish identity and location administration.** The Ontology Studio handover is settled in code as described above (business role and store scope assigned in ZeTSA, identity and administrator status from Studio). Admins can clear a local store assignment with a required reason and audit event; clearing returns store managers and staff to Ontology Studio store claims, while Sales Auditors fail closed with no portfolio until reassigned. Store scoping now also applies to Sales Auditors through their audited local portfolio; internal auditors retain enterprise-wide review access. Automatic orphan detection/reconciliation remains to do, as does validation with real non-administrator Studio users rather than the stub identities used by the HTTP run. Confirm with the retailer how they govern store location traits and assignment changes.
3. **Complete common workspace affordances.** Expand contextual help to a full searchable guide, extend visible-row CSV export to remaining worklists, and add all-matching server exports to remaining queues; keep the current responsive UI and accessibility preferences.
4. **Validate production integrations.** Connect real POS/OMS, bank, and downstream retail/GL systems using their actual contracts; synthetic feeds and a development sink do not prove production interoperability.
5. **Extend the end-to-end lifecycle reviews to the rendered UI.** On a disposable PostgreSQL database, [`test_postgres_store_day_lifecycle.py`](../backend/apps/tests/test_postgres_store_day_lifecycle.py) walks one store day through import with a missing sale, audit (feed gap and GL difference raised), refused early sign-off, a Finance-approved missing-transaction correction, two-person error overrides, re-total, auditor sign-off, two-person closure, export of audited totals and transactions, acknowledgement to Final, and the reopen rules on both sides of acknowledgement (refused once exports are final, allowed and audited while the destination has not acknowledged). [`test_postgres_voucher_lifecycle.py`](../backend/apps/vouchers/tests/test_postgres_voucher_lifecycle.py) covers issue, redemption and escheatment, two stores redeeming one voucher at once (exactly one wins), and redemption racing escheatment. [`test_postgres_ach_lifecycle.py`](../backend/apps/cash/tests/test_postgres_ach_lifecycle.py) covers adjustments settling by destination, HQ-only bank records, and two users reversing one adjustment at once. The earlier PostgreSQL integration tests also pass; they exposed an insert-order hazard in reconciliation case creation and a missing re-validation at rule approval, both fixed. The Alembic migrations (head 0120) apply cleanly to an empty PostgreSQL 18 database, `alembic check` reports no drift from the models, and [`scripts/smoke_lifecycle_http.py`](../scripts/smoke_lifecycle_http.py) then runs the real app under uvicorn against that migrated database with a stub identity server standing in for Ontology Studio. Over HTTP it checks 61 points: authentication and role refusals, import and repeat-delivery safety, opening, cash declaration and deposit, a governed Accounted For total (author cannot approve their own), re-total, early-closure refusal, sign-off, two-person closure, export, acknowledgement and the refusal to reopen a Final day, plus the Studio handover (a plain viewer becomes Finance only through an audited administrator assignment, is never an administrator by assignment, and reverts on removal) and store-role scoping with separate store-manager and store-staff identities carrying assigned stores (their own day readable, another store's day refused, no import, re-total, export, cash declaration or case access, and a store list limited to their store). Running it showed that Over/Short needs an Accounted For total configured before any day can balance; the installed standard totals define only the accountable side, so a re-total now returns, and the Store Day page shows, a warning while no Accounted For total exists (the default is deliberately not seeded, because it would change how existing deployments balance). [`scripts/ui_walkthrough.py`](../scripts/ui_walkthrough.py) then drives the rendered UI in a real browser (Playwright, outside the repo's dependencies): it signs in through Ontology Studio's own login form (credentials from the environment only), seeds the day through the API, and clicks through the screens, 27 checks in all: the re-total warning when Over/Short has no Accounted For side, a governed Accounted For total going live, a clean re-total, auditor sign-off as analyst, closure request as IT, Approve & close as Finance, export, acknowledgement and the Final state, and a render check of the Store Days, Exports, Cash Office, Audit Errors, variance report and configuration screens with no console errors. Where a screen demands a second person, the script records one on the disposable database; the maker-checker rules themselves are proven in the API smoke run. It found a defect that no unit test had: the saved-views endpoint returned a server error for anyone who had never saved a view (now fixed and tested). ### Command Center transaction-gap overview

The auditor Command Center’s selected business date now includes unresolved transaction-number gap counts across authorized store days, excluding gaps with an audited dismissal. It ranks the most affected stores and links directly to the Store Day Missing Transactions tab. The backend applies the signed-in user’s store scope before calculating the summary.

### Over / Short report scaling

The cash Over / Short report now supports an issuing-store filter, server-pages store, register, cashier, and date groups, calculates its headline totals across the complete authorized filter set, and exports all matching groups up to 50,000 rows. The selected store filter applies consistently to paged results, totals, and CSV output (`backend/apps/cash/routes.py`, `frontend/components/OverShortReport.tsx`).

### Store Day review queue recovery

Store Day list-load failures now give role-neutral retry guidance, and failed late/stuck queue requests render a visible retryable error instead of leaving the table in a loading state (`frontend/app/store-days/page.tsx`).
